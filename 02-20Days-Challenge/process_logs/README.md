# process_logs 日志规范

考核明确要求「跨多日连续过程数据」，评委面试时会翻这里的 commit 时间线，所以：

1. **一天一个文件**，命名 `YYYY-MM-DD.csv`，当天采集完就提交，不要事后补。
2. **原始数据直接放进来**，不要只放处理后的汇总表或截图。
3. **异常和报错也要记**：`状态` 列写 `fail` / `error`，`详情` 写清现象。异常数据是面试追问的加分点，藏起来才是减分项。
4. 每份日志开头可用 `日志模板.csv` 的列名，按项目需要增删列。

各项目最低要求（来自考核大纲）：

| 项目 | 连续数据要求 |
| --- | --- |
| 项目一 低功耗终端 | 24 小时以上电池电压/功耗时序 |
| 项目二 视觉检测 | 连续运行推理日志（耗时、置信度、误报） |
| 项目三 声振诊断 | 5 工况 × 15 组原始 WAV/CSV |
| 项目四 校园实用程序 | **连续 ≥7 天**运行日志，每日同步 |
| 项目五 旧电器拆解 | 拆解分步照片 + BOM + 改造接线验证 |
| 项目六 环境监测 | 连续 ≥5 天、每天 ≥12 小时 |
| 项目七 能量采集 | 连续 72 小时充放电曲线 |
| 项目八 助残辅具 | 30 次受限状态盲操原始数据 |

## 补录说明（必须如实交代）

这 5 份日志里，**11-16～11-22 三份是 11-24 追补的**，不是当天提交的。所以：

1. **文件名日期 = 事件发生日**，不是提交日；`git log` 里这些文件的提交时间会晚于文件名日期，这一点不隐瞒
2. 每行都能指回原始证据，来源写在末列「数据来源」：
   - 11-16 来自本人 Word 文档里写明的「11.16」及实物照片
   - 11-21 / 11-22 来自照片水印上的精确时间与分贝值（水印是当时拍的，无法事后补）
   - 11-23 起为实时记录
3. **11-17～11-20 没有记录，不补**。那几天没有可指认的原始证据，编出来就是造假，宁可留着缺口

## 为什么会出现缺口

前期用 Word 文档记录课题，没有版本控制：内容一改就覆盖，也没有按天留档。等建仓时，那几天的细节已经无法复原，只能补结论、补不出过程。这段反思写在 `README.md` 的「为什么建仓偏晚」一节。

## 从现在起的规则

1. **一天一个文件**，命名 `YYYY-MM-DD.csv`，当天结束前提交
2. 事件发生时立刻记，不靠回忆补
3. 每条都写「数据来源」——是实测、是照片水印、还是别人转述
4. 状态列允许 `ok` / `fail` / `pending`；`pending` 表示计划未执行，比空着诚实
